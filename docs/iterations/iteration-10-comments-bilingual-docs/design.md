# 文档架构与发布设计

以下目录、依赖和配置都是未来实施方案，本次不创建配置、不执行构建或部署。

## 一套源文件与两个发布目标

建议采用 Doxygen → XML → Breathe → Sphinx 的 API 链路，指南使用 MyST
Markdown，翻译使用 Sphinx gettext 与 sphinx-intl，主题先试用
`sphinx_rtd_theme`。这套方案利用现有 Markdown，且无需把 C++ 库导入 Python。
Breathe 官方说明了 XML 桥接方式；MyST 和主题的兼容性仍须用本项目试点确认。
[Breathe](https://breathe.readthedocs.io/en/latest/)、
[MyST Parser](https://myst-parser.readthedocs.io/en/latest/)、
[主题文档](https://sphinx-rtd-theme.readthedocs.io/en/stable/)。

不同时维护 MkDocs 和 Sphinx 两套站点，也不在第一轮引入非必需的 API 页面
生成扩展。API 导航先按模块组织，签名由 Doxygen/Breathe 提供，稳定页面与
锚点由站点维护；必要时再评估额外索引工具。

| 拟用位置 | 责任 |
|---|---|
| `docs/site/` | 当前产品文档的独立源目录；首页、指南、API 入口、配置和静态资源 |
| `docs/site/locale/zh_CN/LC_MESSAGES/` | 受版本控制的中文 `.po` 译文 |
| `docs/site/Doxyfile` | 自有公共 API 的提取、排除和警告配置 |
| `docs/requirements-docs.txt` | 独立文档环境的已验证版本约束/锁定入口 |
| `docs/site/maintainer/` | 注释规范、术语、翻译、构建和发布维护说明 |
| `.readthedocs.yaml` | 两个 RTD 语言项目共用的版本化构建入口 |
| `.github/workflows/docs.yml` | PR 双语检查和 GitHub Pages 构建/部署 |
| `docs/_build/` | 被忽略的 XML、gettext 模板、缓存和最终 HTML |

旧的 `docs/iterations`、`acceptance`、`evidence`、`plans` 等继续作为日期档案。
新站只按白名单引用经过核验的小型记录，不递归收录整个旧目录。当前指南迁入
站点时保留可追溯来源；原入口留清晰链接，冻结验收文件不改写，避免两份活跃
教程分开维护。根 README 后续只需新增稳定文档入口，本轮不安排大规模历史重排。

## P127 必须先解决的试点

选择不少于 8 个已有代表符号，涵盖普通函数、重载、配置结构体/字段、枚举、
模板或类型别名，以及所有权/异常/NaN 边界说明；仓库中若有 concept 或受宏
控制的公开接口，也加入样本。不人为修改业务代码来迁就解析器。

试点同时验证签名、默认值、交叉引用、公式、代码块、源码位置链接和中文正文。
至少包含一个安装页、一个小型合成数据教程及一页 API 参考。确认 Doxygen 的
C++23 解析结果与真实头文件一致；无法解析的符号进入明确问题清单，不得悄悄丢弃。

Doxygen 只提取自有公共接口，启用 XML，排除第三方和内部/生成目录，并将
必要文档警告纳入失败条件。配置须注意：`EXTRACT_ALL=YES` 会影响未文档化
告警，不能以“无告警”推断所有 API 已有说明。覆盖统计另与独立公共符号清单
交叉核对。[依据：Doxygen 配置说明](https://www.doxygen.nl/manual/config.html)。

选择在 Read the Docs 和 Actions 上均可安装的已发布兼容版本，锁定 Python
包组合、Doxygen 版本和构建环境，记录实际版本。不能直接把 `latest` 文档
对应的开发版作为依赖。缓存按版本、语言、配置和输入更新，避免旧 XML/译文
造成假通过；至少以一次无缓存构建确认试点。

文档构建不运行 benchmark、不加载用户行情数据、不触发实时服务，也不要求
先编译整个 C++ 库。只有示例验证任务使用 C++ 工具链及必要的现有子模块。
确认注释不依赖第三方源码提取；若少量类型引用需要第三方头文件，只获取明确
依赖，不递归生成其文档或安装 GUI/测试依赖。

## 双语维护流程

Sphinx gettext 可从文档树抽取消息，维护者以 `.po` 翻译并通过语言配置构建。
英文源文档和中文译文纳入 Git；`.pot`、`.mo`、HTML 和 XML 作为再生产物。
[依据：Sphinx 国际化](https://www.sphinx-doc.org/en/master/usage/advanced/intl.html)。

本项目计划使用 `en` 和 `zh_CN` 作为 Sphinx 语言值。英文注释和英文指南是
唯一主源，先提取，再更新中文，最后同时构建。公开页面清单记录页面 ID、
两种语言状态、对应源提交及审阅人；术语表随同维护。正文变化使译文失效时，
应标为待更新，不能沿用旧译文并仍计作完成。

**Breathe 生成的 API 正文能否完整进入 gettext 是待验证项。** P127 要实际
检查摘要、参数、返回、异常、列表、表格和注释中的引用，不只看菜单。
如果选定版本无法覆盖，先评审调整文档链，或采用按完整符号签名绑定的翻译
说明层；该说明层必须检测源注释变化并提供等价中文正文。修订方案通过试点后
才扩大实施。不能以“中文页保留整段英文 API 说明”绕过双语要求，也不把
中英文注释重复塞进每份 C++ 头文件。

符号名和签名不翻译。页面使用稳定 ID，语言切换尽量保留当前页面和版本；
不能无提示地跳到另一个版本。中文搜索要以“回撤”“夏普”等真实词汇测试，
不能只验证英文标识符能搜索到。公式、代码示例、长签名和表格要检查移动端
换行及横向滚动，提供图片替代文字和可见键盘焦点。

不要把文档站和库生成的双语研究 HTML 报告混为一谈；两者的语言配置及产物
不同。迁移页面明确这是原生 C++ 库，没有 Python/pandas 的直接对象兼容承诺，
不把接口数量等同于 Python 全包兼容，也不推导未验证的平台支持。

新教程默认使用很小的合成数据，不下载大数据集；优先引用并验证已有示例，
避免中英文代码各维护一份。基准页面只呈现必要摘要、方法和复现入口，保留
INCONCLUSIVE 等原始结论，不复制完整运行报告或修改历史测量数字。

## Read the Docs 发布方案

采用英文父项目和简体中文翻译项目，指向同一仓库，按平台的 Translations
关系关联。RTD 的多语言模式要求每种语言独立项目。
[依据：RTD 多语言文档](https://docs.readthedocs.com/platform/stable/localization.html)。

计划使用根 `.readthedocs.yaml` 的 v2 配置，明确系统、Python、文档依赖和
Sphinx 入口。两个项目可分别设置项目自定义的非敏感变量
`FINCORE_DOCS_LANGUAGE=en` / `zh_CN`；配置校验值与平台语言设置一致。
这不是假定 RTD 存在同名内置变量。先安装固定工具，再生成 XML 和相应语言的
HTML；警告失败策略与本地一致。
[依据：RTD 配置规范](https://docs.readthedocs.com/platform/stable/config-file/v2.html)。

`latest` 计划跟踪 `dev`；`stable` 仅在已有真实发布标签且双语验证通过后启用，
不由 CMake 版本号推断发布已完成。创建项目、关联仓库/webhook、语言项目和
版本属于后续发布配置工作。项目名与域名可用性尚未检查，不能提前宣布固定
地址已经可访问。Sphinx 的 `zh_CN` 与 RTD URL 语言段分别记录，以实际平台
设置为准，不能直接假设大小写和分隔符相同。

## GitHub Pages 发布方案

使用 Actions 构建两种语言到同一个站点产物，上传后由独立部署任务发布。
PR 只做构建、链接和预览检查；发布仅来自选定分支或发布标签。构建任务只需
读取仓库，部署任务使用 `pages: write`、`id-token: write` 和 `github-pages`
环境；使用官方配置/上传/部署 actions，并在实施时固定经核验的版本或 SHA。
[依据：GitHub Pages 自定义工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)。

规划的项目路径以 `/fincore_cpp/` 为前缀，下面包含英文和中文入口；例如
`/fincore_cpp/en/latest/` 与 `/fincore_cpp/zh-cn/latest/`。这是路径设计，
不是现有线上地址。根入口提供语言选择。语言、版本、搜索、静态资源、404
页面和深层 API 链接都要在该子路径验证，防止只在域名根目录预览成功。

正式标签的双语版本目录应可保留和回滚，`latest` 更新不得删除仍被版本菜单
引用的目录。P133 初期如果没有合适的发布标签，只发布真实存在的 `latest`，
不造出 `stable`。站点产物由 CI 生成，不提交 HTML 到源码分支；上传包符合
Pages 静态产物要求，不包含软/硬链接。

Read the Docs 作为首选规范地址，Pages 作为同源镜像；两者使用相同内容提交，
各自正确设置基路径和 canonical 信息。链接可因托管域名不同而不同，不要求
HTML 逐字节相同。发布记录包含源提交、工具版本、语言、构建任务和真实地址。
某个语言或平台失败时保留上一份已验证站点，明确记录失败组合，不把四个组合
中的一个成功概括成全部上线；重发已验证产物不需要重跑性能基准。

## 维护规则

新增/变更公共 API 时，同一轮更新契约、英文页面、中文译文和公共清单。
新增文档依赖必须经过小型双语回归后更新锁定，不随 CI 的浮动最新版本漂移。
外链检查把临时网络错误与确实删除的目标区分；例外必须有原因、负责人和
复查条件，不能全局屏蔽警告。源码链接绑定发布提交，不指向不断变化的行号。
以上官方资料核对日期为 2026-10-25，实施时再核对平台支持矩阵及配置兼容性。
