# 需求与注释规范

本文件约束迭代 10 的后续实施。本次只写计划，不执行以下源码或配置改动。

## R1 范围与行为保持

范围包括项目自有的 `include/fincore`、`src`、`examples`、`tests`、
`benchmarks`、`tools`，以及实际纳入维护的其他自有 C++/Python 文件。
P126 先按 Git 清单补齐分母，不能把当前统计当成永久固定数量。
排除第三方子模块/库、生成代码、数据集、二进制、构建目录和冻结的历史源码
快照；保留原许可证、版权和第三方署名。公共头中的 `detail` 等内部成员要
明确分类，不能仅因位于安装目录就全部宣称为稳定公共 API。

注释工作不得改变签名、默认值、表达式、算法、常量、异常路径、数据格式、
include 顺序、宏、ABI 或功能范围。不顺手修复问题、不全仓格式化，不以遵循
Google 风格为由重命名接口或改写 C++23 实现。文档构建、测试辅助检查和部署
配置属于另立的文档设施轮次，不能混入“仅注释”提交。

即使文本看起来是注释，也要保留 `noqa`、`type: ignore`、格式化/静态检查
指令、shebang、编码声明和宏续行语义。检查 `__LINE__`、源码哈希和快照绑定
等对位置或字节敏感的使用；不得通过放宽断言来掩盖行为变化。Python docstring
会改变 `__doc__`，不属于纯词法注释，须单独列出允许的文档元数据变化并审阅。

## R2 Google 风格与提取格式

Google C++ 风格强调在声明处说明调用契约，在实现处解释不直观的设计和原因；
无需逐行复述代码或为显然的访问器堆砌注释。私有函数也不自动豁免契约说明。
C++ 函数首句按隐含主语 “This function” 写，以 “Computes …” 或 “Returns …”
这类动词短语开头，而非命令式 “Compute …”。写作应简洁、完整、与实际行为
一致。[依据：Google C++ 注释规范](https://google.github.io/styleguide/cppguide.html#Comments)。

本项目据此作以下**项目约定**：源代码说明以英文为主，中文通过文档翻译维护；
公开 API 使用 `///` 文档注释，较长现存 `/** ... */` 可保留；实现内使用 `//`。
这是为 Doxygen 提取而选定的形式，不是声称 Google 强制使用 Doxygen。
[Doxygen 支持的文档块](https://www.doxygen.nl/manual/docblocks.html)用于统一提取规则。

| 位置 | 必须说明的内容 | 避免的做法 |
|---|---|---|
| 模块/复杂类型 | 用途、数据模型、重要不变量、所有权和适用范围 | 只写“某某类”；拷贝整份设计文档 |
| 函数声明 | 可观察行为、输入和返回契约、非显然的失败/副作用 | 从名字猜测行为；复制实现步骤 |
| 枚举、选项和配置字段 | 选项含义、单位、范围、默认值效果、选项间约束 | 给枚举名换一种拼写而没有新信息 |
| 模板/重载 | 类型约束、与其他重载的区别、共同契约的可追踪引用 | 多份相同说明逐渐漂移 |
| 实现内部 | 数值技巧的原因、边界分支、算法不变量、取舍依据 | “循环遍历数组”等逐句翻译 |
| 测试 | 不明显的 oracle、回归背景、固定种子和验证边界 | 把测试名称重复一遍 |
| 示例、基准、工具 | 输入/输出、运行前提、复现方法、测量或清理范围 | 把本机成功写成跨平台保证 |

按需使用 `@param`、`@tparam`、`@return`、`@throws`、`@pre` 和 `@note`。
参数标记必须与签名匹配；`void` 不生成空的返回段。不能为了填满标签编造异常、
线程安全或复杂度保证。可用链接复用共同契约，但调用者应能在 API 页面找到
对应解释，不能依赖未发布的本地文件。TODO 应指向具体问题与处理条件，不能
替代当前契约或充当本轮修复承诺。

下面是写作顺序模板，尖括号内容是待核实的占位说明，不是任何现有接口的契约：

```cpp
/// Returns <the observable result, described in one sentence>.
///
/// <Explain units, alignment, missing values, and ownership when relevant.>
/// @param input <Required shape, ordering, and lifetime.>
/// @return <Meaning, units, ordering, and ownership of the result.>
/// @throws <Verified exception type> <Verified failure condition.>
```

Python 工具采用 Google 风格的模块/函数 docstring，按实际需要写 `Args`、
`Returns`、`Yields` 和 `Raises`；简单且含义明确的函数可以不重复说明。
[依据：Google Python 注释与 docstring 规范](https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings)。
不新增 Python 绑定，不把开发工具文档写成可 `import fincore_cpp` 的用户 API。

## R3 金融与数值契约

逐个接口核实以下适用项，不能把一条“全局约定”硬套到例外函数：

- 收益率、百分比、价格、权重和金额的单位；频率、年化因子、无风险收益及时间口径。
- 时间戳/时区、索引排序和唯一性；列名、数据类型、形状、多输入对齐及缺失列行为。
- 空输入、样本不足、NaN/Inf、零方差、除零、重复值、ties 和窗口预热规则。
- 可变性、复制/视图、所有权、引用或 `span` 的有效期；资源和会话关闭后的行为。
- 数值稳定性、容差、随机种子、收敛/失败状态；仅在有依据时承诺复杂度或并发安全。
- 文件覆盖/拒绝策略、异常清理、编码、序列化版本、缓存键与失效条件。

判断顺序为当前实现、针对该行为的测试、当前已接受的契约，再参考历史说明。
出现冲突时登记问题并等待审阅，不能把疑似 bug 包装成有意设计，也不能在注释
轮中修复代码。没有足够依据的承诺不得发布为确定事实。

## R4 双语内容

英文为主源，简体中文为完整用户语言。两者必须具有一致的页面清单、接口列表、
示例行为、限制和版本信息。公共 API 的解释性正文也要翻译，不能仅翻译导航，
或把英文回退当作中文覆盖。代码标识符、头文件名、命令参数和数学符号保留原样。

术语表应覆盖 returns/收益率、drawdown/回撤、volatility/波动率、horizon/预测期、
turnover/换手率、exposure/暴露、annualization/年化等，并记录项目中的具体含义。
机器翻译只能作为草稿；由理解接口的人检查单位、否定条件、异常、边界及金融术语。
修改英文契约时，同轮更新译文或阻止该页面进入正式双语发布。

## R5 文档产品与发布

交付首页、安装/消费包、快速开始、数据契约、模块指南、API 参考、Python 迁移、
性能方法、排错与贡献指南。API 页面关联公共头文件和稳定符号锚点，指南提供
可复制的小型合成数据示例。安装教程要区分首次下载依赖与离线构建，以及核心库
与可选 ImPlot。文档工具不能成为核心 CMake 消费者的必装依赖。

Read the Docs 与 GitHub Pages 使用同一提交和同一内容源；主地址、语言和版本
映射清晰。公开页面不得包含本机绝对路径、私有输入、失效证据链接或大规模
benchmark 输出。历史计划与验收记录保留日期和原始状态，不批量改写或翻译
冻结证据，也不默认将整个 `docs/` 纳入站点。

性能介绍必须注明数据规模、工作量、CPU/线程设置、环境、统计和噪声结论。
目前[单 HTML 基准记录](../../acceptance/2026-10-25-alpha003-html-benchmark.md)
中两种规模都因噪声判为 INCONCLUSIVE；不得概括为所有场景稳定快 30 倍。
历史 CSV 与现行 HTML 是不同工作量，不拼成一组成绩。

来源、当前行为、预期依据、影响和证据等级，由审阅者决定是文档问题、真实
