# 迭代 9：需求

**版本：** R1，2026-10-25。**本轮状态：** 按用户最新指令收尾；实现已分轮交付，剩余正式性能验收与优化延期，见[收尾记录](closeout.md)。以下保留原需求。
关联：[总览](README.md)、[设计](design.md)、[验收](acceptance.md)。

## R1 — 性能目标与比较范围

1. 相对固定 Python fincore 基线，500 文件和全量 alpha003 的完整研究流程
   均须达到至少 30 倍；分别争取 100 倍。最低交付与进取目标分开记录。
2. 主成绩包含进程启动/导入、原始 CSV 加载、因子计算、数据准备、研究分析、
   所有约定表的导出、文件关闭及进程退出。编译、独立结果比较不计入。
3. 同一机器、相同 CPU affinity、一个逻辑处理器，不让另一个 SMT 线程承载
   并行候选任务；Python 数值库和 C++ 库的计算线程限制为一，验证实际限制。
4. 主场景使用对称预热的文件缓存；每次仍启动新进程并读取原始数据。冷启动
   单列，只有缓存状态确实受控才称“冷缓存”。内存内核和等核数多核试验也单列。
5. CPU 时间、峰值内存、分配和 I/O 指标用于解释墙钟表现，不与墙钟混为同一量。
   不将“无显式线程”或 MSVC `std::clock()` 当成运行时 CPU 预算证明。

## R2 — 固定数据与完整工作量

- 数据保持 5,471 个 CSV、243 个交易日；500 文件按既有确定性均匀抽样。
  数据文件清单、内容摘要、日历、样本顺序、命令参数在 P111/P112 固定。
- 保持 alpha003：横截面 open/volume 平均并列百分位秩、10 个完整配对样本、
  稳健相关系数；`end_offset=22`、`next_open_to_open`、周期 1/5/20、5 分位、
  `cross_section_rank`、稳定性 lag 1/5/20 和原有有效性规则。
- 完整表集：factor_values、signals、labels、ic、ic_summary、quantile_returns、
  spreads、turnover、stability、coverage、diagnostics，以及必要 manifest。
  P112 为每张表定义规范 schema、行键、列、顺序、缺失值和输出格式。
- 保留 Python 已有的 Pearson IC、rank IC、各周期 turnover 与研究明细；
  C++ 补齐差异或通过显式导出适配保持等工作量，不以删减 Python 工作量达标。
  新增/调整输出的必要成本须进入计时，不能在计时后补算缺失指标。
- 现有 NaN 标签行、稳定性汇总、coverage 结构差异必须在 P112 明确并对齐；
  当前“共同有限单元相等”不等于整个结果集完全等价。
- 两边统一 CSV 编码、换行、时间文本、列与数值精度策略。无需跨语言 CSV
  每字节相同，但允许的表示差异、文件数/行数/字节数必须报告；不得降低精度
  或压缩/省略 C++ 必需输出而仍使用原来的完整输出成绩名称。

## R3 — 数值与行为保持

主数值默认沿用现有绝对误差 `1e-6`，同时报告实际最大误差及误差分布；不能
因优化失败而放宽。NaN/Inf、缺失掩码、重复键处理、索引/列顺序、并列秩、
分位边界、有效样本、时区和无未来数据泄漏规则单独精确比较。
稳定性历史二级 `1e-3` 不能掩盖样本集合不一致；先统一定义，再在相同集合上
按主数值预算验收。新增 Pearson/汇总指标在实现前用小型 oracle 冻结预算。

跨 horizon 只共享兼容的顺序、索引或缓冲；必须按各自有效样本重建 tie rank
和 quantile 边界。滑动统计优化须覆盖近常量、大偏移、缺失与长序列漂移。
不默认开启 `/fp:fast` 等改变 NaN 或重排语义的全局选项。

## R4 — 可复用实现与资源

- 性能实现进入可复用的库内路径；benchmark 只负责数据装载、调用、测量和比较。
  alpha003 专用因子内核的成绩与库研究路径分别报告。
- 优先在内部增加紧凑表示、显式 source-row 索引和工作区；公开接口返回值的
  拥有权、调用方修改隔离、错误语义、稀疏数据能力与可安装性保持。
- 不把某个数据文件名、预期结果、固定股票数量或观测到的因子值写入快捷路径；
  不跨调用缓存计算结果来绕过完整流程。可缓存不可变元数据，但建缓存成本
  必须属于相应冷/热场景，不能偷偷移出主计时。
- 默认完整流程峰值内存不得超过 P112 同规模 C++ 参考值的 110%；若高于该值，
  先优化或提交明确的资源权衡修订，不能静默回归。稀疏案例不得意外全量稠密化。

## R6 — 工作流与目标保持

直接修改现有 `dev`。每轮只解决一个可验收的实现问题：实测/审阅通过后提交
明确文件或 hunks，再开始依赖它的下一轮；保护无关改动，子模块先提交再更新父
gitlink。每轮记录 scope、基点、验收结果、分项/整体收益、分支与 commit。

当前只完成计划不代表性能完成。后续未达到 30 倍必须继续定位差距或诚实记录
未达标；不能把 13–17 倍、测试全绿或某个内核超过 100 倍当作最低目标完成。
100 倍是持续探索的进取目标，只有对应完整场景实测通过才标达成。
